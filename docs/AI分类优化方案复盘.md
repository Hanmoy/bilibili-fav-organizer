# B站收藏整理台 · AI 分类优化方案复盘

> 从「启发式截词」到「两阶段分类 + 分类均衡约束」—— 10 轮迭代的完整技术演进记录
> 版本：v0.10.0 · 2026-08-22

---

## 一、项目背景

**产品形态**：B站收藏夹整理油猴脚本（Tampermonkey）。核心链路：

```
抓取收藏夹全部视频 → AI 自动分类 → 预览确认（可编辑）→ 移动到分类收藏夹
```

**核心矛盾**：用户收藏 600+ 视频后「收藏即吃灰」，需要自动归类。但 AI 分类要同时满足三个目标，它们互相拉扯：

| 目标 | 失败表现 |
|---|---|
| 分类**覆盖**所有视频 | 未分类堆积（一度 390/614） |
| 分类**精简**不冗余 | 出现「游戏/游戏竞技/独立与休闲游戏/电竞」四胞胎 |
| 分类**精准**不错分 | 「AI编程」里混入艺考生爆改男友 |

## 二、演进历程：9 轮迭代的踩坑记录

### v0.2 · 启发式截词（严重 bug）
**问题**：AI 不可用时，用正则从标题提取 2-4 字片段当分类名 → 「为什么积」「实测对比」「每天一遍」这种荒谬收藏夹。

```ts
// ❌ 罪魁祸首：标题截词当分类名
const words = m.title.match(/[\u4e00-\u9fa5]{2,4}/g) || [];
// 「为什么积不出来？切比雪夫判别法」→ 提取出「为什么积」
```

**教训**：**宁可不分类，也不要瞎分类**。该逻辑彻底删除，AI 不可用时规则未命中一律进「未分类」。

### v0.3 · 策略改为「AI 为主」
规则引擎（用户自写关键词）只做无 AI 时的兜底，未命中进「未分类」。**预览结果可编辑**（改名/移动/新建/删除分类）后再应用。

### v0.4 · 双模式 + 繁简合并
- **全量整理（full）**：合并所有视频 → AI 重新分类 → 可新建收藏夹
- **增量分配（incremental）**：只归入已有收藏夹，绝不新建
- 新增 `src/utils/zh.ts`：零依赖繁简映射表，「做饭」自动并入已有「做飯」

### v0.5 · 全量语义修正
用户明确：全量 = **忽略已有收藏夹，AI 自由构建完整分类体系**。但此时仍是「每批独立设计分类」→ 冗余爆发。

### v0.6.0 · 批间分类名延续
发现「AI与编程/AI技术/AI与技术」冗余根因：**分批喂 AI，每批独立设计分类体系**。引入 `establishedCats` 批间延续，分类数 49→18。同时 bvid 优先匹配（AI 输出 id 不可靠）。

### v0.6.1 · 候选名池（帮了倒忙）
把用户已有收藏夹名（15+ 个）作为「候选分类名」塞给 AI → 弱模型被误导，**未分类反而恶化**。教训：**给弱模型的参考信息越少越好**。

### v0.6.2 · 弱模型防漏输出
**390 未分类暴增**，数据反推根因：**AI 只输出了一部分视频的分类就截断**（每批 100 条 + prompt 过长）。

修复：
- 批大小 100 → 50
- 未分类**分批多轮补充**（≤50/批，最多 3 轮）
- 候选名池限 6 个
- prompt 强制「输出前逐条核对 ID/BV号」

### v0.7.0 · 两阶段分类（最终方案）★
**根治冗余与错分**：从「每批边分类边建类」改为「先全局设计体系，再严格按体系归类」。

## 三、最终方案：两阶段分类架构

```
全部视频标题
    │
    ▼
┌─────────────────────────────────────────┐
│ 阶段1 · 全局分类体系设计 (aiDesignCategories) │
│  AI 一次性通读全部 614 条标题              │
│  输出 10~18 个分类名（JSON）              │
│  约束：同类合并 / 禁杂项 / 主题一致        │
└─────────────────────────────────────────┘
    │  固定分类体系 fixedCategories
    ▼
┌─────────────────────────────────────────┐
│ 阶段2 · 严格按体系归类 (aiClassify)        │
│  分批（≤50/批），每批只能使用体系内分类    │
│  禁止新建 / 禁止杂项 / 逐条核对 ID         │
│  未分类视频 → 补充循环（≤3轮）            │
└─────────────────────────────────────────┘
    │
    ▼
分类结果（未分类 0 · 16 个合理分类 · 失效独立成类）
```

### 阶段1 核心代码

```ts
// src/service/ai.ts
export async function aiDesignCategories(
  cfg: AiConfig,
  allTitles: string[],          // 全部视频标题（只传标题，不传 id，降低输入量）
  existingFolders: string[],    // 已有收藏夹名（仅命名参考）
  userRequirement = '',
): Promise<string[]> {
  const prompt = `请通读全部 ${allTitles.length} 条标题，设计 10~18 个分类：
- 分类名简洁（2~6 字）、语义明确
- 同一分类内视频主题必须一致（发现宽泛必须拆）
- 同类必须合并（"游戏"和"游戏竞技"只能留一个）
- 禁止"其他/杂项/综合"垃圾桶分类
- 覆盖全部视频内容`;

  // 调 OpenAI 兼容接口，解析返回的 { categories: [...] }
  const cats = (parsed.categories || []).map(c => c.trim()).filter(Boolean);
  return cats.slice(0, 18);     // 硬上限 18
}
```

**关键点**：阶段1 **只传标题不给 id**——大幅压缩输入量（614 条标题约 2 万字符），弱模型才能完整阅读；输出只有分类名数组，结构简单不易截断。

## 四、关键技术细节

### 4.1 视频匹配：bvid 优先，id 兜底

公益站弱模型输出的数字 id 经常不可靠（幻觉/错位），但 BV 号（如 `BV1AodfByE7D`）是模型从标题语境中能正确复述的稳定标识。

```ts
const src =
  (v.bvid && batch.find(m => m.bvid === v.bvid)) ||   // ① bvid 精确匹配
  batch.find(m => !m.bvid && m.id === v.id) ||        // ② 无 bvid 时 id
  batch.find(m => m.id === v.id);                     // ③ 兜底
```

### 4.2 分批策略：小批 + 多轮补充

**弱模型的截断规律**（从 390 未分类数据反推）：单次输入超过 ~3000 字时，模型倾向于只处理前一部分就停止输出。因此：

| 参数 | 值 | 理由 |
|---|---|---|
| 主批大小 | 50 条 | 50 条标题 ≈ 1500-2500 字，弱模型可完整处理 |
| 补充轮次 | ≤3 轮 | 每轮只处理上一轮未分类的，直到无进展 |
| 补充批大小 | min(50, aiBatchSize) | 未分类可能几百条，必须再拆小批 |

```ts
// 补充循环：最多 3 轮，每轮按 ≤50/批 重新喂 AI
for (let round = 1; round <= 3 && uncMedias.length; round++) {
  // 分小批 → 逐批 aiClassify → 从未分类中移除 newly
  if (newly.size === 0) break;  // 本轮无进展说明 AI 卡住，停止
}
```

### 4.3 候选名池限流

用户收藏夹名（做飯/計算機/健身/考研…）**最多只传 6 个**给 AI。原因：
- 超过 6 个 → prompt 变长 → 触发弱模型截断
- 名字太多 → 模型被误导，倾向只在名字里选，选不中就不输出

```ts
const aiRefs = existingFolders.slice(0, 6);
```

### 4.4 繁简/近义合并

`src/utils/zh.ts` 零依赖实现：

```ts

  // 「做饭」→「做飯」✅  「计算机」→「計算機」✅

```

### 4.5 全量模式分类名合并（回退保险）

两阶段成功时体系已全局去重；若阶段1 失败回退为逐批自由分类，靠归一化合并兜底：

```ts
// 1) 完全相等 / 包含（游戏 ⊂ 游戏竞技，AI ⊂ AI编程）
// 2) 共享 2 字核心词（健身运动 vs 健身训练）
```

### 4.6 失效视频独立成类

B站 API 返回 `attr` 字段标记视频状态（0 正常 / 1 已删除 / 9 发布者删除）。失效视频单独归入「失效视频」收藏夹，不参与分类，用户确认后统一移动。

## 五、方法论：如何用「导出复盘」驱动迭代

本项目的核心调试循环（对你有直接复用价值）：

```
1. 导出分类预览 MD（含每个视频的分类 + 来源收藏夹）
2. 数据反推根因：
   未分类多  → 是 AI 没输出（漏）还是输出没匹配（id错）？
   分类冗余  → 是不是分批导致的批间建类不一致？
   分类错分  → 是不是候选名池误导 / 垃圾桶分类诱导？
3. 针对根因改一处，不要同时改多处（否则无法归因）
4. 重新跑，导出 MD 对比量化指标：
   分类数 / 未分类数 / 失效数 / 单个分类最大体积
```

**量化指标表**（历次迭代的真实数据）：

| 版本 | 分类数 | 未分类 | 主要问题 |
|---|---|---|---|
| v0.5 | 49 | 241 | 批间重复建类 + id 匹配失败 |
| v0.6.0 | 18 | 98 | 候选名缺失导致健身/考研滞留 |
| v0.6.1 | 17 | 390 | 候选名池误导弱模型 → 截断漏输出 |
| v0.6.2 | 35 | 0 | 分类仍冗余（35 个） |
| **v0.7.0** | **16** | **0** | 基本可用，少数错分 |

## 六、经验教训总结

1. **给弱模型的 prompt 越短越好**：候选名池 15+ 个 → 6 个；参考信息能不给就不给
2. **先设计体系、再批量归类**（两阶段）远胜于「边分类边建类」（单阶段）——这是分类质量提升的最大杠杆
3. **宁可不分类，不要瞎分类**：截词建类是最恶劣的失败模式
4. **稳定标识优于数字 id**：bvid 匹配让 AI 幻觉 id 不再致命
5. **小批 + 多轮补充**是弱模型漏输出的通用解法
6. **改一处、量一次**：每轮只动一个变量，用「分类数/未分类数」量化验证

## 八、已落地优化：分类均衡约束（v0.7.1）

**背景**：两阶段分类后分类数收敛（16 个），但出现「AI编程 70 个」「社会时评 62 个」这类超大分类——半垃圾桶效应。弱模型把拿不准的视频全塞进最大分类。

**思路**：双保险——① 阶段1 设计体系时就让 AI 预估分类规模，超大类直接拆；② 阶段2 分类完成后程序化扫描，超阈值分类日志提示用户。

### 8.1 阶段1：分类规模预估（prompt 约束）

```ts
// src/service/ai.ts · aiDesignCategories
const prompt = `... 请设计 **10~18 个**分类：
- 分类名简洁（2~6 字），语义明确
- **分类均衡**：总视频数约 ${allTitles.length} 条，
  平均每个分类约 ${Math.max(5, Math.round(allTitles.length / 14))} 条。
  请据此预估每个分类的视频规模，确保每个分类大致容纳 5~70 条——
  **如果一个分类会聚集超过 70 条视频，说明它太宽泛，
  必须拆分成 2 个以上更精确的分类**（如"AI编程"聚集过多时
  拆出"AI工具评测""编程语言教程"等）
...`;
```

**关键点**：把「总条数 ÷ 目标分类数」算出的**平均规模**告诉 AI，让它在设计阶段就感知每个分类应该装多少视频——这比事后拆分更自然，因为 AI 是在「知道全部内容」的前提下设计体系的。

### 8.2 阶段2：程序化超大分类检测（兜底）

```ts
// src/service/classify.ts · classifyAll 末尾
// ---- 超大分类检测（分类均衡约束的兜底）：>70 条提示用户拆分 ----
const OVERFLOW_THRESHOLD = 70;
for (const [cat, items] of Object.entries(finalResult)) {
  if (cat === UNC || cat === '失效视频') continue;   // 未分类/失效不算
  if (items.length > OVERFLOW_THRESHOLD) {
    logs.push(
      `⚠️ 分类「${cat}」有 ${items.length} 条，超过 ${OVERFLOW_THRESHOLD} 条阈值` +
        `——可能混入了不相关视频。可在预览中逐条移到正确分类，` +
        `或重新整理时在「整理要求」里提示拆分该分类`,
    );
  }
}
```

**设计取舍**：为什么不自动拆分超大类？
- 自动拆分需要再次调 AI 对子集做二次归类 → 增加 API 成本 + 可能引入新错分
- 超大分类的「错分重灾区」通常集中在十几条，用户在预览里手动移动更快更准
- 所以采用**日志提示 + 引导手动处理**，而不是自动化

## 十一、v0.9.0 变更记录（2026-08-22，真实使用反馈驱动）

用户反馈三个问题：刷新后分类结果丢失；移动中切换页面中断/按钮卡死；分类准确度与效率。

| 类别 | 变更 |
|---|---|
| 持久化 | 任务快照（分类结果/重复副本/日志）写入 GM 存储，刷新或重开页面后自动恢复预览 |
| 断点续跑 | 移动按「分类×源夹」分组执行，每组成功即落盘 `appliedItems`（条目级幂等）；中断后按钮变「继续移动剩余视频」，重跑自动跳过已移动条目 |
| 状态机 | `busy` 模块变量（切 tab 后旧闭包卡死按钮的根因）改为 `task.applying`，视图轮询刷新；移动中 `beforeunload` 拦截整页导航；「放弃本次整理」入口 |

## 十三、v0.11.1 变更记录（2026-08-23，增量模式 bug 修复）

基于用户真实增量整理预览（勾全部夹 / 仅勾默认收藏夹，均 100% 未分类）定位并修复。

### 13.1 Bug：增量模式全部视频进未分类

**现象**：勾选默认收藏夹（或任意夹）跑增量 → 预览 100% 未分类；勾全部夹同样 100% 未分类。

**根因**：`classify.ts` 阶段2 主循环（387 行）与补充轮（440 行）将 AI 候选名池强制截断为 `existingFolders.slice(0, AI_PARAMS.CANDIDATE_POOL)`（前 6 个收藏夹）。该约束是 v0.6.1 为**全量模式命名参考**设计的（避免弱模型被长列表迷惑），但被**错用到增量模式**——增量模式语义是"已有夹 = 唯一合法目标集"，截断后 AI 只见过前 6 个夹，无法输出与后位夹匹配的名字，收尾 `matchExistingFolders` 全匹配不上 → 全进未分类。

**排除项**：两份预览均无"跳过 N 条旧视频"日志，说明 `folderLastRun` 为空（首次跑增量），非基准把视频全跳过。

**修复**：增量模式候选池 = 完整 `existingFolders`；全量模式保持 `slice(0,6)` 不变。

```ts
// 387 行（主循环）
const aiRefs = mode === 'incremental' ? existingFolders : existingFolders.slice(0, AI_PARAMS.CANDIDATE_POOL);
// 440 行（补充轮）同步修改；576 行补类循环本就在 mode==='full' 守卫内，无需动
```

**验证**：tsc 零错误 + vite build 成功，产物 0.11.1（150.06KB / gzip 41.59KB）。收尾匹配逻辑（480-493 行）本身正确，无需改。

### 13.2 反思（对应提示词体系缺漏）

这正是之前分析过的"约束被错搬场景"——`CANDIDATE_POOL≤6` 在全量命名参考场景成立，但增量的"文件夹名=唯一合法目标集"是另一种语义，直接复用导致功能失效。应在提示词/规格中显式区分"候选名池（参考用，可截断）"vs"权威目标集（不可截断）"。

### 13.3 待真机验证

## 十四、v0.11.2 变更记录（2026-08-23，增量空分类根因修复）

用户反馈：装 0.11.1 跑增量**仍然是 100% 未分类**。排除 0.11.1 修复未生效（产物已确认含完整候选池），重新通读 `classify.ts` 主循环 + 收尾匹配 + `ai.ts` 增量 prompt，**锁定真正的根因**。

### 14.1 真根因：增量 prompt 强约束逼弱模型输出空分类

**铁证三连**（用户确认）：
1. 版本 0.11.1 对 → 候选池修复已生效，非"没装对新版"
2. 无"跳过 N 条旧视频"日志 → 非 folderLastRun 基准把视频全跳
3. 无"未匹配已有收藏夹"警告 → 收尾匹配段未触发，说明 `result` 除 UNC 外**无 key** → 主循环 `for` 没写入任何非 UNC 分类

**代码链**：主循环（393-413 行）靠 `v.bvid / v.id` 匹配 batch 视频写入 `result[key]`；收尾（480-493 行）对增量模式用 `matchExistingFolders(newNames, existingFolders)` 重组——若 `result` 除 UNC 无 key，则 `newNames` 为空、match 不触发、警告一个都不打 → **正好就是"100% 未分类 + 零警告"**。全量模式走 494-536 另一分支且本身有阶段1体系，故正常。

**根因定位**：`ai.ts` 增量 prompt（原 231-252 行）的组合约束：
- `必须一字不差使用已有收藏夹准确名称`（含繁简差异）
- `严禁新建！所有视频只能放入已有收藏夹`
- 列出**完整夹名（几十个）** 让模型盲选

弱模型在这组"怕选错/怕新建/怕漏"的强约束下，对不确定视频选择**最安全策略 = 不输出任何分类** → `categories: {}` 或全 `"未分类"` key（被 407 行 `if (key === UNC) continue` 跳过）→ 主循环 for 不执行 → 全进 UNC。

**关键认知**：0.11.1 修的"候选池截断"只是表象之一（让后位夹有机会被选中），但真凶是 prompt 约束本身把模型逼到"输出空集"。这也是为什么"修了截断还是一样"——模型连前 6 个夹都不选，直接输出空。

### 14.2 修复：放宽增量 prompt + 诊断日志

**`ai.ts` 增量 prompt 重写**（231-252 行）：
- 删 `必须一字不差` / `严禁新建` 等死约束 → 改为"选最贴合内容主题的一个已有夹，系统自动归并近似名称（繁简兜底），不必纠结一字不差"
- 删 `只要内容沾边就必须` 强制措辞 → 改为"优先归入，近似即可，系统兜底"
- 保留"绝不遗漏：必须输出每一个视频"和"确实无法归入才未分类"
- 保留"归类按内容主题而非标题关键词"的反例提醒（与全量一致）

**`classify.ts` 主循环后新增诊断**（425 行后）：增量模式若 `result` 除 UNC 无有效分类，emit 明确警告，引导用户看 AI 思维链或在「整理要求」中写放宽指示。

### 14.3 验证

- tsc 零错误 + vite build 成功，产物 0.11.2（150.53KB / gzip 41.98KB）
- **未做真机分类验证**（无登录态），依赖用户装 0.11.2 跑一次确认；若仍空，诊断日志会打印 AI 思维链，可直接定位是"模型仍不敢输出"还是"引用匹配问题"

### 14.4 反思（提示词体系视角）

这次"修 A 没用，真凶是 B"的排查过程，暴露了之前提示词体系的另一个盲区：**只验证"功能是否触发"（候选池传了没），没验证"AI 在 prompt 约束下会不会正常产出"**。弱模型对强约束的"投降式输出（空/全默认）"是一种特殊失败模式，应在 REVIEW 模板里加一条" prompt 约束是否过强导致模型不敢输出 / 输出空集"。
